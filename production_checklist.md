# Production Feature Verification Checklist

Use this page as the verification source of truth for ZayOS production readiness. The goal is not only to confirm that screens exist, but to prove each feature is wired to real behavior, correct permissions, reliable data, and clear user-facing states.

## How To Verify

For each row in the checklist:

1. Open the route or workflow in the running app.
2. Perform the expected action as the listed role.
3. Confirm the expected output using UI evidence and, where possible, backend/API/database evidence.
4. Mark the status using the verification fields below.
5. Record evidence with a screenshot path, route, API response, database row, or source file reference.
6. If a feature is mock-only, static, seed-only, or unsupported, mark it honestly instead of treating the visible UI as complete.

## Verification Status Fields

Add these fields beside each checklist item during verification, either directly in this file or in a copied audit table.

| Status Field   | Allowed Values                                   | Meaning |
| -------------- | ------------------------------------------------ | ------- |
| Current Status | Working / Partial / Broken / Missing / Mock Only | Whether the feature works end-to-end right now. |
| Priority       | P0 / P1 / P2                                     | P0 blocks production readiness, P1 is important, P2 can follow. |
| Backend/API    | Ready / Partial / Missing / Unknown              | Whether real backend support exists and is connected. |
| Permission     | Verified / Missing / Wrong / Not Applicable      | Whether role access and restrictions were checked. |
| Data State     | Real / Seed / Mock / Static                      | Whether the visible data is production-like and persisted. |
| Fix Needed     | Yes / No                                         | Whether engineering work is required. |
| Evidence       | Screenshot / Route / File / API response         | The proof used for the verification result. |

## Verification Rules

- Do not mark a feature as `Working` based only on a static UI.
- Use `Mock Only` when data is hardcoded, seed-only, or not connected to persistence.
- Use `Partial` when the page exists but one of validation, persistence, permissions, error handling, or evidence is missing.
- Use `Missing` when the route, UI, or backend flow does not exist.
- Use `Broken` when the feature exists but fails during the expected action.
- For unsupported features, either remove the UI or mark the gap clearly.
- P0 items should be verified before broad UI polish or lower-priority workflows.
